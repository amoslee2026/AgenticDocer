# ADR-009：规模化存储策略（分区、索引与保留）

- **状态**：已接受（2026-09-16，依用户批注 A8 及澄清）
- **决策者**：用户（批注 + 澄清「纯 PG + 分区/调优，保留现选型」）
- **影响范围**：§4 DDL、§5 部署、ADR-002（纯 PG 选型）、B10（规模基线）

## 背景

批注 A8 要求规模提升：

> [!TODO] 规模改为 支持10000个Agent/bot，上万份文档

用户澄清口径：**「10000」为已注册 agent 身份总额（非并发写入者数）**；「上万份文档」为真实增长预期。

**量化冲击**（依据实测 7 份语料 ≈9.4k 原子校准，≈1,343 原子/文档）：

| 维度 | 原基线 B10 | 新目标 | 倍数 |
|---|---|---|---|
| 文档 | ≤500 | **10,000** | 20× |
| 节点 | ≤100k | **≈13.4M** | **134×** |
| 存储 | — | **20–54 GB** | — |
| 身份 | 1（无鉴权） | **10,000** | — |

**关键判断**：13.4M 行、20–54GB 对 PostgreSQL 16 属**中等量级**（单表亿行级才是瓶颈区），故 **ADR-002 的「纯 PG」选型不变**，无需引入分布式/列存/外部检索引擎。但需三项针对性措施。

## 决策

### 1. 分区（按增长热点）

| 表 | 分区键 | 分区方式 | 理由 |
|---|---|---|---|
| `nodes` | `doc_id` | LIST（按 doc_type 或 hash 子分区） | 查询几乎总带 `doc_id`；单文档节点数稳定（~1.3k），分区大小均衡 |
| `events` | `ts` | RANGE（按月） | append-only 且按时间查询（diff/重放/审计）；便于冷数据归档与 DROP PARTITION |
| `comments` | — | 不分区 | 量小（与批注人数相关，非文档量级） |
| `docs` / `refs` / `assets` / `terms` / `users` | — | 不分区 | 量级可控（10k / 数百万 / 数百万 / 千级 / 10k） |

**分区实现**：PG 16 声明式分区（`PARTITION BY LIST` / `RANGE`）。`nodes` 若 LIST 分区键基数太大（10k 文档），改用 **HASH 分区 64 个**（`PARTITION BY HASH (doc_id)`），兼顾均衡与维护成本。

**外键注意**：PG 分区表的外键引用需谨慎——`refs.dst_node_id → nodes(node_id)` 跨分区外键在 PG 16 受支持（分区表作为被引用方要求唯一索引包含分区键）。**决策**：`refs` 对 `nodes` 的外键**降级为应用层校验**（M09B `broken_refs` 巡检兜底），避免分区键侵入唯一索引。这是**有意的权衡**：牺牲 DB 层强约束，换取分区灵活性 + 巡检兜底（已在 §3 M09B 中有 `broken_refs` detector）。

### 2. 索引调整

- `nodes`：`(doc_id, ordinal)` 在分区内仍有效；`text_fts` GIN **保留但改为分区局部的表达式索引**（存疑：GIN 在 13M 行 × 分区后建索引成本高 → 改为**每分区并行建**，migrate 脚本需处理）；
- `events`：`(entity, entity_id, ts)` 分区裁剪后仍有效；新增 `(ts)` 用于归档扫描；
- `refs`：`(dst_doc_id, dst_node_id)` 保留；新增 `(src_node_id)`（外键降级后遍历需显式索引）；
- **不建** `nodes.content` 的 GIN（jsonb_path_ops）——13M 行下 write amplification 不划算，且该索引服务的是「按 content 内字段查询」这一当前不存在的访问模式。

### 3. 连接与运行时调优

| 项 | 值 | 依据 |
|---|---|---|
| `max_connections` | 200 | 并发写入者 ≤50 × 余量 |
| 应用连接池 | `pool_size=20, max_overflow=10`（每 worker） | 单 worker 上限 30；避免连接风暴 |
| `shared_buffers` | 8 GB（机器内存 ≥32GB 时） | 惯用 25% |
| `work_mem` | 64 MB | 排序/哈希连接（`doc_id` 聚合） |
| `maintenance_work_mem` | 1 GB | 分区索引构建 |
| `autovacuum` | `nodes`/`events` 调高 `autovacuum_vacuum_scale_factor=0.05` | 高写入表需要更积极回收 |
| 批量导入 | `COPY` + 单事务分批（每 5k 行） | M03 导入 10k 文档时避免长事务与 WAL 膨胀 |

### 4. 数据保留

- `events`：**RANGE 按 ts 保留 24 个月**，超期分区 `DETACH` + 归档（`pg_dump` 到 `archive/`）后 `DROP`——append-only 表用分区 DROP 而非 DELETE，避免膨胀；
- **不建快照表**（沿用原决策，13M 节点下事件重放仍足够；若重放延迟超标再引入物化视图）。

## 后果

**正面**：
- 保持单一 PG 实例（运维简单，与 LightRAG 同库不变）；
- 分区裁剪使 `doc_id` 查询与时间范围查询保持索引级性能；
- `events` 归档成本从「DELETE 亿行」降为「DROP 分区」；
- 无需分布式/外部检索引擎（选型不变，评审风险低）。

**负面 / 代价**：
- **DDL 复杂度上升**：分区表 + 分区管理脚本（新月份自动建分区，需 `pg_partman` 或自研定时任务）；
- **外键降级**：`refs→nodes` 失去 DB 强约束，依赖 M09B 巡检（已有 `broken_refs` detector）；
- **迁移成本**：现有 alembic 迁移需改写为分区创建；
- **索引构建时间**：13M 行 GIN 索引首次构建需并行/离线策略。

**风险**：
- HASH 分区的跨分区查询（如「全局按 ordinal 排序取前 N」）会有轻微开销——当前无此访问模式，风险可控；
- 10k 文档导入的批量策略若不当（单事务），会导致长事务与 WAL 膨胀——已列 `COPY` + 分批决策。

## 备选方案与否决理由

| 方案 | 否决理由 |
|---|---|
| 重新评估存储引擎（列存/ES/Mongo） | 13M 行远未到 PG 瓶颈；推翻 ADR-002 + 全 DDL + LightRAG 同库假设，返工面极大且无实测证据支持 |
| 先探针实测 10k 文档再定 | 更稳健但多一阶段；量化推演（134× 于已验证的 100k 基线）已足够支撑分区决策，实测作为**验收环节**保留（性能基准脚本含 10k 文档场景） |
| 不分区，仅加索引 | 13M 行单表 + GIN 索引的 vacuum/维护成本高；events 无归档手段会无限增长 |
| 引入 `pg_partman` 自动分区管理 | **未否决**——列为 M03/§5 部署的可选依赖，若自研定时任务成本更高则采用 |
