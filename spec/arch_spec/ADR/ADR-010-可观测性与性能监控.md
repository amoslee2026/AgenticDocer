# ADR-010：可观测性架构（Agentic Logger 集成 + 性能评估与监控）

- **状态**：已接受（2026-09-16，依用户要求「要支持 agentic logger！要有性能评估和监控机制」）
- **决策者**：用户（直接要求）+ 架构评审
- **影响范围**：全模块（M01–M11）、§6 横切关注点、CLI（§9.2）、部署（§5）、性能指标（§1.4）

## 背景

### 1. 日志要求的既有约束

`AGENTS.md`（项目级强制）：「日志子系统实现必须用 Agentic Logger SDK」。原架构（v1.2）仅在 §6 横切表列了一行引用，**未定义集成方式、字段映射、查询路径**，属「声称满足但无设计」状态。用户本次明确要求「要支持 agentic logger」。

### 2. 监控的空白

v1.3 的 §1.4 定义了量化指标（点查 P95 <200ms、章节渲染 <1s、鉴权 P95 <10ms 等），但**无任何测量机制设计**——没有「谁来测、何时测、结果存哪、超标怎么办」的定义。指标不可测 = 不可验收（违反 it.idea 的 KPI 完整铁律）。

### 3. 规模变更的放大效应

B9 将规模提升 134×（≥10,000 文档 / ≈13.4M 节点）。在此量级下，「性能劣化不可见」会直接导致生产事故，监控从「锦上添花」变为「必需能力」。

### 4. AgenticLogger 的事实（源码级核实，2026-09-16）

| 能力 | 事实 |
|---|---|
| 包名/版本 | `agentic-logger`（PyPI）；`license = "PolyForm-Noncommercial-1.0.0"`（与本仓库**同协议**） |
| 核心 API | `AgentLogger(program, command, storage)`；方法 `info/warn/error/debug/tool_call` |
| 结构化字段 | `module`、`error_code`（`ErrorCode` 枚举）、`dur`、`exit`、`tool`、`cmd`、`rid`（请求/trace id）、`seq`、`pid` |
| 存储 | JSONL（默认）/ SQLite（build/test/ci 自动选择） |
| 查询层 | CLI（`agentic-logger stats/trace/query`，支持 `--group-by`、TSV 输出省 token）/ MCP server（`pip install "agentic-logger[mcp]"`） |
| 跨进程 | `trace --rid` 沿 `rid` 跨文件串联调用链 |
| 跨语言 | Bash/Rust/Go/TS/SystemVerilog/Tcl SDK，字节兼容 JSONL（`sdks/INTERCHANGE.md` 为规范） |
| 文件布局 | `{program}_{command}_{YYYYMMDD}_{HHmmssffffff}.jsonl`，一 run 一文件，append-only |

**关键契合点**：`rid` 天然映射到本系统的**请求级追踪**（一次 API 调用贯穿 M10 鉴权 → M06/M07 → M02 存储 → M04 渲染）；`error_code` 枚举可映射本系统的 `Violation.rule_id` 与业务错误码；TSV 输出对 coding agent 消费友好（与本项目「agent 自诊断」目标一致）。

## 决策

### 1. 全面接入 Agentic Logger SDK（用户裁决）

**所有模块**的统一日志出口：

```python
# agenticdocer/observability/logger.py
from agentic_logger import AgentLogger, ErrorCode

def get_logger(module: str, **ctx) -> AgentLogger:
    """模块级 logger 工厂。program="agenticdocer"，command=<模块或子命令>。
    自动注入 rid（来自请求上下文 ContextVar）+ module（M## 标识）。"""
```

| 模块 | `command` | 关键 `module` 值 |
|---|---|---|
| M01 | `model` | `m01.schema`、`m01.anchor` |
| M02 | `store` | `m02.nodes`、`m02.events`、`m02.comments` |
| M03 | `import` | `m03.parser`、`m03.rules`、`m03.assets` |
| M04 | `render` | `m04.render`、`m04.section`、`m04.normalize` |
| M05 | `retrieve` | `m05.traverse`、`m05.search` |
| M06/M07 | `api` | `m06.router`、`m07.router` |
| M09 | `validate` | `m09a.engine`、`m09b.quality` |
| M10 | `auth` | `m10.verify`、`m10.session`、`m10.rbac` |
| M11 | `cli` | `m11.cli` |
| M-LR | `export` | `mlr.export`、`mlr.stream` |

**字段映射（本系统 → AgenticLogger）**：

| 本系统概念 | AgenticLogger 字段 | 说明 |
|---|---|---|
| 请求/trace id | `rid` | 每 HTTP 请求或 CLI 调用生成一次，贯穿全链路 |
| 模块标识 | `module` | `M##.子域`（见上表） |
| 业务错误码 | `error_code` | 扩展 `ErrorCode`：`DTO_*` 前缀（如 `DTO_ANCHOR_CONFLICT`、`DTO_AUTH_REJECTED`） |
| 校验违规 | `error_code` | 映射 `Violation.rule_id`（如 `RULE_ANCHOR_DUP`） |
| doc_id | 自定义字段 `doc_id` | 所有文档相关日志必带 |
| 耗时 | `dur`（毫秒） | API/查询/渲染/验签均记录 |
| 工具调用（CLI 子命令） | `tool_call(tool=<cmd>, cmd=<args>, exit=<rc>, dur=<ms>)` | M11 CLI 统一埋点 |

**审计分离原则（重要）**：Agentic Logger 记录的是**运行日志**（debug/info/error，可轮转、可丢弃）；**审计事件仍落 PG `events` 表**（`entity='auth'`/`doc`/`node`…，append-only、不可丢弃）。两者不可互相替代——日志用于诊断，events 用于权威追溯（P2）。

### 2. 请求级追踪（rid 贯穿）

```
HTTP 请求 / CLI 调用
  → 生成 rid（uuid7 短形态，8 hex）
  → M10 验证（dur, error_code）
  → M06/M07 路由（dur）
  → M02 存储（dur, 慢查询阈值 warn）
  → M04 渲染（dur, 章节级）
  → 响应（总 dur, status）
所有日志行共享同一 rid ⇒ `agentic-logger trace --rid <id>` 一次拉出全链路
```

**CLI 自诊断**（供 coding agent 排查，§9.2 扩展）：

```bash
agenticdocer logs stats --group-by error_code   # 错误分布
agenticdocer logs stats --group-by module       # 模块健康度
agenticdocer logs trace --rid <rid>             # 单请求全链路
agenticdocer logs tail --module m02.nodes       # 实时跟踪
agenticdocer logs query --level ERROR --since 1h
```
以上均为 `agentic-logger` CLI 的**薄封装**（传递 `--log-dir`、默认 program 过滤），不重复实现查询逻辑。

### 3. 性能评估机制（三层）

#### 3.1 在线指标（持续，轻量）

| 指标 | 采集方式 | 存储 |
|---|---|---|
| API 请求耗时（按端点，P50/P95/P99） | M06/M07 中间件记 `dur` → AgenticLogger | JSONL 日志 |
| 错误率（按端点 × `error_code`） | 同上（`level=ERROR`） | JSONL 日志 |
| 慢查询 Top-N（>阈值） | M02 `store/query.py` 包装器，`dur > SLOW_QUERY_MS` 时 `warn` | JSONL 日志 |
| 鉴权失败率 | M10 `verify_signature` 失败计数（`error_code=DTO_AUTH_*`） | JSONL 日志 + PG `events(entity='auth')` |
| 渲染耗时（整档 vs 章节） | M04 `render_document`/`render_section` 计时 | JSONL 日志 |
| 导入进度与覆盖率 | M03 每 N 条输出 `info(msg="progress", ...)` | JSONL 日志 |

**观测端点**：`GET /api/v1/admin/metrics?since=&window=`（**admin 专属**）——聚合最近窗口的指标快照（从 AgenticLogger 查询层读取，不引入额外时序库）。

#### 3.2 离线基准（`tests/perf/`，可复现，验收依据）

| 基准 | 内容 | 对应指标 |
|---|---|---|
| `bench_point_query.py` | 语料全量入库后固定查询集（≥100 次）取 P95 | §1.4 点查 P95 <200ms |
| `bench_render.py` | 整档 + 单章节渲染计时（最大文档 CXL 3.59MB） | 章节 <1s、整档 <3s |
| `bench_auth.py` | Ed25519 验签 + PG 会话查（≥1000 次） | 鉴权 P95 <10ms |
| `bench_scale.py` | **合成 10,000 文档灌入**（ADR-009 规模验收）→ 测点查/渲染/存储 | B9 规模目标 + 分区有效性 |
| `bench_import.py` | 7 份真实语料 + 合成语料的导入吞吐与解析覆盖率 | 覆盖率 ≥95% |

**运行**：`uv run pytest tests/perf/ -m perf --benchmark-json=build/perf.json`；结果归档 `build/perf/`（gitignore），趋势对比由 `bench_scale.py --compare` 完成。

#### 3.3 容量与健康巡检（M09B 扩展）

| 巡检项 | 方式 | 频率 |
|---|---|---|
| 表/分区行数与膨胀 | `pg_stat_user_tables` + `pg_total_relation_size` | 启动 + 按需 |
| 索引使用率（未用索引发现） | `pg_stat_user_indexes`（`idx_scan = 0`） | 按需 |
| autovacuum 滞后 | `pg_stat_user_tables.last_autovacuum` 与 `n_dead_tup` | 启动 + 按需 |
| 连接池饱和度 | 应用侧 `pool.checkedout()/size()` 采样 | 请求期 |
| 分区完整性（未来月份分区是否已建） | 检查 `events` 分区存在性 | 启动（缺失则告警） |
| events 归档逾期 | 最老分区 vs 24 个月保留策略（ADR-009） | 启动 + 按需 |

**输出**：`agenticdocer stats --health` 打印巡检报告；超标项以 `error_code=DTO_*` 计入日志。纳入 M09B 质量门的 detector 集合（`perf_health` detector）。

### 4. 阈值与告警语义

**不引入外部告警系统**（单机自包含，用户裁决）。超标行为定义：

| 级别 | 触发 | 行为 |
|---|---|---|
| `warn` | 单次耗时 > 指标 × 0.8 | 日志 `warn`（计入慢查询 Top-N） |
| `error` | 单次耗时 > 指标 | 日志 `error` + `error_code=DTO_PERF_EXCEEDED` |
| `critical` | 窗口内 P95 > 指标 × 1.5 | `stats --health` 输出「不达标」+ 建议（分区/索引/连接池） |

**验收挂钩**：`bench_*.py` 的结果即为 §1.4 指标的验收证据；CI/本地提交前跑 `bench_point_query` + `bench_render`（快基准），`bench_scale` 按需（慢，~分钟级）。

## 后果

**正面**：
- 指标**可测可验**（此前 §1.4 是不可执行的口号）；
- `rid` 全链路追踪：一个命令定位「哪个环节慢/错」，无需人工 grep 串联；
- 日志结构化为 JSONL/TSV，对 **coding agent 消费友好**（token 省 ~46%，符合本项目 agent-first 定位）；
- 与 AgenticLogger **同协议**（PolyForm NC 1.0.0）、同语言、同生态，无许可冲突；
- 无外部依赖（无 Prometheus/Grafana/ELK），单机自包含。

**负面 / 代价**：
- **新增依赖** `agentic-logger`（Python 包）+ 可选 `[mcp]` extra；
- 每请求多一次日志写入（JSONL append，开销可控；已含在鉴权 <10ms 预算外）；
- 日志文件增长（需轮转策略：按大小/天数保留，落 `logs/`，gitignore）；
- 需为 `ErrorCode` 扩展 `DTO_*` 业务码并保持与 `Violation.rule_id` 的一致映射（维护成本）。

**风险**：
- **审计与日志混淆**的风险：若把审计当日志存，日志轮转会**销毁审计证据**。已用「审计分离原则」明确隔离（`events` 表为唯一审计权威源）；
- AgenticLogger 为**单人维护的早期项目**（v0.1.4）——按项目「插件选型成熟度评估」规则，其 GitHub stars/下载量偏低。**缓解**：日志为**可替换基础设施**（封装在 `observability/logger.py` 单一适配层），若项目停更可在该层切换到 stdlib + 结构化 formatter，业务代码零改动。此为**有意的权衡**：换取 agent-first 的日志消费体验与同生态一致性。

## 备选方案与否决理由

| 方案 | 否决理由 |
|---|---|
| stdlib `logging` + JSON formatter | 需自行实现 trace/查询/stats；丧失 agent 友好的 TSV 与 `trace --rid`；**且 AGENTS.md 已强制要求 AgenticLogger** |
| 引入 Prometheus + Grafana | 单机私有部署引入外部依赖与运维面；用户裁决「自包含」 |
| ELK / Loki 栈 | 同上，且对单机 13.4M 节点规模属过度工程 |
| 仅关键路径埋点 | 无法覆盖 §1.4 全部指标（尤其鉴权/渲染细粒度） |
| 把性能数据存 PG 表 | 与「日志是运行态、事件是权威态」的分离原则冲突；且高频写放大 PG 负担 |
