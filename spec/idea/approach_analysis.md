# 方案分析与选型

生成：2026-09-16（it.idea 完整模式）。决策矩阵量化见 `trade_off_matrix.md`；选定方案的结构细节见 `design_doc.md`。

## 方案 A：自研模块化单体（PG 权威库 + WebUI + Agent 接口）

**核心思路**：完整落地 v0.1 设计——结构化内容库（PG/JSONB）为唯一权威源，渲染层确定性产出 Markdown，agent 走结构化读写接口（lint 闭环），自研 WebUI 承载评审/批注/追溯，LightRAG 语义索引边界后置。

**优点**：
- 直接对齐 v0.1 全部五项问题（P1–P5）的解法，无设计债
- 内容原子 + 渲染分离 = 格式合规成为工具保证（P1 根治）
- 引用图在库内可精确多跳（P4），批注解耦（P3）
- 模块化单体（M01–M09）符合 Agent-aware 知识库推荐（单 Agent/中小规模），实现单元清晰

**缺点**：
- 建设量最大（后端 + 前端 + 解析器 + 渲染器）
- WebUI 表单引擎为自研风险点（Q3）
- 语料入库前的解析器（M03）是质量瓶颈（半自动缓解，B11）

**适用场景**：知识库要长期演进为主力资产，且已有明确设计（v0.1）。

## 方案 B：渐进文件方案（markdown + git + lint，DB/WebUI 后置）

**核心思路**：先不建 DB/WebUI；以 `spec/` markdown + git 评审 + markdownlint/Vale 为最小闭环，用脚本做引用检查（`traces_to` 以 frontmatter 表达）；结构化库与 WebUI 按需再建。

**优点**：
- 数天内可用（低建设量）；对 7 份语料立刻能做一致性/引用校验回归
- 零新基础设施（复用 git/现有脚本栈）
- 完全规避 Q3/Q5 未决风险

**缺点**：
- P1 只做到"事后 lint"而非"结构性保证"——agent 仍直写 markdown 文本
- P3 评审只有 git diff（行级，非 node 级）；批注无处承载
- P4 多跳检索不可能精确（frontmatter 引用靠脚本扫描，无图）
- 与 v0.1 「内容与呈现分离」核心原则冲突；后续迁移成本高（schema 未定前的数据会长歪）

**适用场景**：只想先要"可用的规范文档管理"，不追求结构化知识库。

## 方案 C：现成工具组合（strictdoc/Doorstop + 检索 + VSCode 批注）

**核心思路**：不自研 WebUI，用开源需求/文档工具（strictdoc 的 SDoc 语法 + traceability）承载结构化，配 lightRAG 检索与已装的 VSCode `spec-feedback` 扩展做批注评审。

**优点**：
- 复用成熟工具（traceability 现成）；建设量中等偏低
- VSCode 批注链路已有资产（用户已装 spec-feedback）

**缺点**：
- SDoc 语法面向自己的文档模型（requirement 为中心），**行业标准规范**（PCIe 3.4MB 巨文档、register 表、状态机）灌入需要强适配，掰弯工具
- 无数据库原子模型 → P2/P4 的精确引用图仍缺；渲染层仍要自研（导出格式受限）
- 工具边界导致 schema 受制于人（v0.1 三类文档异构性 P5 无法自由建模）
- 长期看是"两个系统拼接"（工具 + 补丁），演进摩擦大

**适用场景**：需求追溯占主导、文档类型单一、接受工具约束。

## 推荐：方案 A（自研模块化单体）

**理由**：
1. v0.1 已把架构核心决策做完（PG+JSONB、内容原子、自研 WebUI、LightRAG 边界），A 是唯一与之对齐的路径；B 与 v0.1 核心原则冲突，C 的模型不匹配异构文档目标（P5）。
2. 风险点（Q3 表单引擎、Q5 模板引擎）是**局部可裁决**的技术细节，不改变架构方向，且都有降级路径（自研轻量引擎）。
3. 渐进性由**实施顺序**（design_doc §12）而非降级架构承担：先 M01/M02/M03/M04 跑通"7 份语料 → 结构化 → 渲染"闭环（即可开始用 GigaRAG 语料测试，满足用户「先开发再测试」的节奏），WebUI 与检索随后。
4. Agent-aware 证据：模块化单体（≤10 模块、单 Agent 开发）为该知识库的推荐模式；Python/FastAPI/PG/React 均为推荐栈。

**实施顺序建议**（依赖关系，非工期）：

- **阶段 1（地基+闭环）**：M01 内容模型（含 M09A 校验引擎）→ M02 存储 → M03 导入解析 → M04 渲染。里程碑：7 份语料全链路往返测试通过（规则覆盖率 ≥95%，见 design_doc §10）。
- **阶段 2（人机接口）**：M06 Agent 接口（含 lint 闭环）→ M07 API 契约 → M08 WebUI 前端。M06 与 M07/M08 可并行（契约先行）。
- **阶段 3（增值）**：M05 检索（多跳）→ M09B 质量门 → M-LR 联调（C7 解禁后）。
- **关键依赖路径**：M01 → M02 → M03 → M04 → M06 →（WebUI / 检索 / LightRAG）。
- **并行可能性**：M05 与 M09B 在 M04 后可并行；M08 前端仅依赖 M07 契约。
