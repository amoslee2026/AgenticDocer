# ADR-009：规模化存储策略（分区、索引与保留）

- **状态**：已接受（2026-09-16，依用户批注 A8 及澄清）
- **决策者**：用户（批注 + 澄清「纯 PG + 分区/调优，保留现选型」）
- **影响范围**：§4 DDL、§5 部署、ADR-002（纯 PG 选型）、B10（规模基线）

## 背景

批注 A8 要求规模提升：

> [!TODO] 规模改为 支持10000个Agent/bot，上万份文档

用户澄清口径：**「10000」为已注册 agent 身份总额（非并发写入者数）**；「上万份文档」为真实增长预期。

**量化冲击**（依据实测 7 份语料 ≈9.4k 原子校准，≈1,343 原子/文档）：

| 维度 | 原基线 B10 | 新目标 | 倍数 |
|---|---|---|---|
| 文档 | ≤500 | **10,000** | 20× |
| 节点 | ≤100k | **≈13.4M** | **134×** |
| 存储 | — | **20–54 GB** | — |
| 身份 | 1（无鉴权） | **10,000** | — |

**关键判断**：13.4M 行、20–54GB 对 PostgreSQL 16 属**中等量级**（单表亿行级才是瓶颈区），故 **ADR-002 的「纯 PG」选型不变**，无需引入分布式/列存/外部检索引擎。但需三项针对性措施。

## 决策

### 1. 分区（按增长热点）

| 表 | 分区键 | 分区方式 | 理由 |
|---|---|---|---|
| `nodes` | `doc_id` | **HASH 64 个** | 查询多带 `doc_id`；单文档节点数稳定（~1.3k），分区均衡。（**V16**：`node_id` 单列点查无法裁剪，见下「读路径约束」） |
| `events` | `ts` | RANGE（按月） | append-only 且按时间查询（diff/重放/审计）；便于归档（**不 DROP**，见 §4） |
| `comments` | — | 不分区 | 量小（与批注人数相关） |
| `docs` / `refs` / `assets` / `terms` / `users` 等 | — | 不分区 | 量级可控 |

**分区实现**：PG 16 声明式分区。`nodes` = `PARTITION BY HASH (doc_id)` 64 个分区。

**外键处置（V3 修复，完整清单）**：分区化后**以下外键在 PG 16 全部无法成立**（引用分区表要求被引唯一约束含分区键）——原「`refs→nodes` 跨分区外键受支持」的断言**错误，已删除**：

| 外键 | 处置 |
|---|---|
| `nodes.doc_id → docs(doc_id)` | **保留**（docs 不分区） |
| `nodes.parent_node_id → nodes(node_id)` | **降级**（M09B 校验孤儿 parent） |
| `refs.src_node_id / dst_node_id → nodes(node_id)` | **降级**（M09B `broken_refs`） |
| `comments.node_id → nodes(node_id)` | **降级**（同上） |
| `comments.target_event_id → events(event_id)` | **降级**（events 分区，PK 含 ts） |
| `terms.definition_node_id → nodes(node_id)` | **降级**（同上） |

**主键调整**：`nodes` PK → **`(node_id, doc_id)`**；`events` PK → **`(event_id, ts)`**。**§4 基础 DDL 的这两处定义以此节为准**（勿按未分区版本实现）。

**events 分区兜底（V3）**：**预建未来 3 个月分区 + 配 DEFAULT 分区**（缺分区不致写入失败）；维护失败由 M09B `perf_health` 巡检告警（`DTO_PARTITION_MISSING`）。

**读路径约束（V16 修复）**：`nodes` 按 `doc_id` HASH 后，**按 `node_id` 单列点查无法分区裁剪**（需探测 64 分区）——而 `GET /api/v1/nodes/{node_id}` 正是 M06 主端点。**规定**：① 应用层维护 `node_id → doc_id` 轻量映射表（或 `node_id` 哈希的副本索引表）以先定位分区；② `bench_point_query.py` **必须含「按 node_id 单列点查」用例**；③ 删除原「跨分区开销无此访问模式」的错误表述。

### 2. 索引调整

- `nodes`：`(doc_id, ordinal)` 分区内有效；`text_fts` GIN **裁决（V23 修复）**：**保留** STORED 生成列 + GIN（M-LR 导出与 M09B 质量门在用），但**明确迁移期构建程序**——先 `COPY` 灌数据、再**每分区并行** `CREATE INDEX`（`maintenance_work_mem=1GB`，逐分区提交），避免 13M 行一次性构建的锁与内存压力；**删除原「存疑」表述**（已裁决，非未决）；
- `events`：`(entity, entity_id, ts)` 分区裁剪后有效；新增 `(ts)` 用于归档扫描；
- `refs`：`(dst_doc_id, dst_node_id)` 保留；新增 `(src_node_id)`（外键降级后遍历需显式索引）；
- **不建** `nodes.content` 的 GIN（jsonb_path_ops）——13M 行下 write amplification 不划算，且无对应访问模式。**判据一致性说明（V23）**：与上条不矛盾——FTS 列**有确定消费者**（M-LR/M09B），content GIN **无任何消费者**。

### 3. 连接与运行时调优

| 项 | 值 | 依据 |
|---|---|---|
| `max_connections` | 200 | 按 10k 身份 × 活跃率推导（**V18 修正**：原「并发写入者 ≤50」非用户澄清内容，实为本设计假设——用户仅澄清「10000=身份总额非并发」）。取值：并发读 ≈100、**写入峰值 ≤20**（写路径少且短事务）；最终以 `pg_stat_activity` 实测为准。 |
| 应用连接池 | `pool_size=20, max_overflow=20`（每 worker，单 worker 上限 40） | **V18**：原 `20/10`（上限 30）先于目标封顶，不自洽。默认 2 worker → 总上限 80 < 200。 |
| `shared_buffers` | 8 GB（机器内存 ≥32GB 时） | 惯用 25% |
| `work_mem` | 64 MB | 排序/哈希连接（`doc_id` 聚合） |
| `maintenance_work_mem` | 1 GB | 分区索引构建 |
| `autovacuum` | `nodes`/`events` 调高 `autovacuum_vacuum_scale_factor=0.05` | 高写入表需要更积极回收 |
| 批量导入 | `COPY` + 单事务分批（每 5k 行） | M03 导入 10k 文档时避免长事务与 WAL 膨胀 |

### 4. 数据保留（V4 修复——关键修正）

**`events` 是权威溯源（P2），永久保留，不因时间 DROP。**

原「24 个月后 `DETACH` + `DROP`」与「重放=当前态」（REQ-M02-F03）、版本历史/diff（REQ-M07-F05/F06）、批注 `target_event_id` 锚定（REQ-M02-F05）**直接矛盾**——DROP 后旧节点重放结果为空集 ≠ 当前态，M09B 巡检将全量误报，旧版本 diff 不可得。**修正为**：

- 超期分区**仅做存储层归档**：`DETACH` → 迁至 `events_archive` 表空间（或 `pg_dump` 冷存），**逻辑上仍参与重放**；
- 查询视图 `events_all = events UNION ALL events_archive`，重放/历史/diff 一律走此视图；
- **禁止**用「归档」作为丢失历史的理由；若未来确需物理删除，**必须同时**修改 REQ-M02-F03、REQ-M07-F05/F06 的验收口径并显式声明重放边界。

- **不建快照表**（沿用原决策，13M 节点下事件重放仍足够；若重放延迟超标再引入物化视图）。

## 后果

**正面**：
- 保持单一 PG 实例（运维简单，与 LightRAG 同库不变）；
- 分区裁剪使 `doc_id` 查询与时间范围查询保持索引级性能；
- `events` 归档成本从「DELETE 亿行」降为「`DETACH` 分区」（**不 DROP**，见 §4）；
- 无需分布式/外部检索引擎（选型不变，评审风险低）。

**负面 / 代价**：
- **DDL 复杂度上升**：分区表 + 分区管理脚本（新月份自动建分区，需 `pg_partman` 或自研定时任务）；
- **外键降级**：`nodes`/`refs`/`comments`/`terms` 共 6 处 FK 失去 DB 强约束（**V3**：完整清单见 §1），依赖 M09B 巡检兜底（`broken_refs` + 孤儿 parent 校验）——这是本次分区化**最大的完整性代价**；
- **迁移成本**：现有 alembic 迁移需改写为分区创建；主键含分区键的调整牵连 6 处引用；
- **索引构建**：13M 行 GIN 首次构建采用「先 COPY 后逐分区并行 CREATE INDEX」，需 `maintenance_work_mem=1GB` 与维护窗口（已裁决，非未决）；
- **点查路径复杂化（V16）**：`node_id` 单列点查需先经映射表定位 `doc_id`，多一跳；

**风险**：
- HASH 分区下 **`node_id` 单列点查需探测多分区**（V16：**这是实际存在的主访问模式**，非「无此访问模式」）——已规定映射表方案 + 基准必测项；若实测 P95 超标，触发备选（`node_id` 雪花前缀携带 doc 分片 / 全局索引表）；
- `events` 归档后重放需 UNION `events_archive`（V4）——重放查询复杂度上升，`events_all` 视图封装之；
- 10k 文档导入的批量策略若不当（单事务），会导致长事务与 WAL 膨胀——已列 `COPY` + 分批决策。

## 备选方案与否决理由

| 方案 | 否决理由 |
|---|---|
| 重新评估存储引擎（列存/ES/Mongo） | 13M 行远未到 PG 瓶颈；推翻 ADR-002 + 全 DDL + LightRAG 同库假设，返工面极大且无实测证据支持 |
| 先探针实测 10k 文档再定 | 更稳健但多一阶段；量化推演（134× 于已验证的 100k 基线）已足够支撑分区决策，实测作为**验收环节**保留（性能基准脚本含 10k 文档场景） |
| 不分区，仅加索引 | 13M 行单表 + GIN 索引的 vacuum/维护成本高；events 无归档手段会无限增长 |
| 引入 `pg_partman` 自动分区管理 | **未否决**——列为 M03/§5 部署的可选依赖，若自研定时任务成本更高则采用 |
